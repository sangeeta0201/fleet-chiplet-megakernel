## Three structural byte levers the roofline exposes

**1. Routing imbalance costs 0.58 ms of the floor.** Top-8 over 8 ranks averages
one activated expert per rank, but the layer's makespan is set by the busiest
rank, and 8 balls in 8 bins has an expected max near 3. Expert-*parallel* is the
wrong decomposition at batch 1. Splitting each activated expert's weights across
all 8 ranks (tensor-parallel *within* an expert) makes every rank read exactly
8 × per_expert / 8 = one expert-equivalent, with zero variance. This converts a
0.58 ms stochastic tax into a deterministic one and is the single largest item
the roofline shows.

**2. The shared expert is replicated on all 8 ranks** — 20.05 MB/layer/rank, the
same size as the entire *mean* routed load. Sharding it saves ~17.5 MB/layer =
1.3 GB/iter ≈ **0.25 ms**.

**3. `q_a_proj` is the largest replicated attention tensor at 12.98 MB/rank** —
bigger than the already-sharded `o_proj`. It is a down-projection, so an output
shard is clean; a K shard needs a reduce. With `kv_a_proj` and `router` the
replicated attention total is 18.25 MB/layer/rank ≈ **0.26 ms**.

Those three together are worth ~1.1 ms of floor. They matter — but note that
even taking *all* of them still only moves the floor from 2.32 to ~1.6 ms, while
the measured gap is 9.1 ms. **Bytes are not the problem. The schedule is.**

## What the gap actually is

Prior measurement on this branch, all recorded in memory:

- ~29% of a layer is barrier wait; no phase uses all 232 workers.
- Barrier *mechanics* are measured out twice: deleting 0.51 ms of counted W13
  barrier moved the wall 0.10 ms; all-thread polling cost +0.73 ms twice.
- Tile widths are saturated — the W13 tile is at 74% of the per-CU HBM share,
  and narrowing to OPW=16 lost 1.34 ms.
- Cutting work *inside* a phase is absorbed: five ceiling probes, and only
  deleting a whole 16-worker serial phase moved the wall.

That last point is the diagnosis. The kernel is bulk-synchronous: every worker
marches through the same phase sequence, so a phase that only has work for 16 of
232 workers stalls 216 of them, and shaving that phase's work changes nothing
because the barrier still waits for the slowest arriver.

**This is precisely the thing TileRT designed away.** Their published mechanism
is *heterogeneous workers*: inside GLM-5.1's attention layer they run a Sparse
Indexer worker group and MLA worker groups **concurrently**, as different worker
types, rather than forcing every stage into one execution abstraction. Plus
collectives pushed into the tile flow instead of being external stages.

So the lever is task #30: **give up the bulk-synchronous shape.** Partition the
232 workers into concurrent groups running *different* phases of the same layer
(or of adjacent layers) at once, so a 16-worker phase costs 16 workers' time
instead of 232 workers' wall clock.
